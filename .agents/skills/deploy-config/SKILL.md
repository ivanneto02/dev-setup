# Deploy configuration on this machine

Use this repository's `scripts/deploy-config.sh` for file activation. Read `AGENTS.md`, `README.md`, `workflow/status.md`, and `docs/deploy-config.md` first. This skill is not itself permission to deploy: **inspect, preview, summarize every intended live change and its backup/rollback, and request explicit approval before `--apply`**. If the user's request already explicitly approves a defined set of paths and effects, stay within that scope; ask before expanding it. Do not treat a request to create or load this skill as approval to change the environment.

1. Identify the actual host (`uname`, OS release), user, home directory, restrictions, installed tools and versions, active configuration paths and overrides. On macOS, inspect both Ghostty's XDG and Application Support paths and their load order. Do not assume that the inspection host is the target or that an Arch installation applies to a Mac.
2. Compare each candidate source to the live file. Select only validated tools. The script supports Neovim's main `init.lua` plus lockfile, Ghostty, Kitty on Arch, and tmux. Bash is **not deployable** yet: `config/bash/.bashrc` contains unsafe machine-specific CUDA paths and TERM changes. Do not install packages, fetch plugins, start Neovim (which can bootstrap dependencies), enable services, or change Pi/Limen/Herdr, provider routes, or credentials as part of this script. Inspect those separately and ask approval for their specific effects if needed. The mobile Neovim alternative and Kitty backup are not managed.
3. Give `--tool` for each selected tool. For Ghostty, pass the active absolute target with `--ghostty-dest`; it must be under the target home. The script's default is preview. Check its output, missing prerequisites and conflicting paths; explain which files will be linked, backed up or left unchanged, and where application overrides may take precedence. Stop if any target cannot be validated. Do not make up a Mac install path or claim Mac runtime validation from Linux tests.
4. After approval, run the **same command** with `--apply`. It creates per-file sibling backups with `.pre-dev-setup-*` suffix and links repository files. Inspect the links and the affected application using safe, tool-specific checks; a successful link alone does not prove the application works. Do not trigger plugin downloads or change active shell startup without separate approval. Re-run the preview to check idempotence.
5. Report exactly what changed, paths and backups, any application reload needed, what checks actually passed, what remains untested, and how to unlink and restore each backup. If partial deployment fails, inspect actual files before rollback; do not delete unrelated or later user edits.

This workflow applies user-level files, not system installation. Worktrees are not sandboxes. Never copy secrets or session state into Git. `docs/deploy-config.md` has destination and precedence details. GitHub issues #1, #3, #4, #5, #6 and #10 track target decisions, unsafe Bash, terminal behavior, Neovim validation, safe setup and Pi skill discovery; do not mark them complete merely because this skill exists.
